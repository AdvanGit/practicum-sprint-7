## Требования безопасности к интеграции с внешними системами

*Далее: PropDevelopment - интегратор (как клиент), SmartHomeLimited (как пример) - поставщик услуги (как сервер)*
#### Определение отношений

**Функции интегратора:**
- передача управляющих команд на открытие домофона, двери, или шлагбаума
- передача биометрических данных поставщику
- передача номерных знаков поставщику
- передача данных для регистрации домофонов поставщику услуг
- получение потокового видео для визуальной идентификации лица от поставщика услуги

**Функции поставщика услуги:**
- потоковая передача видео интегратору
- получение управляющих команд для управления устройствами
- регистрация домофона за пользователем и хранение идентификаторов
- хранение данных, идентифицирующих пользователя
- хранение биометрических данных
- хранение номерных знаков

*Интегратор не хранит данные биометрии, номерных знаков, а предоставляет интерфейс для работы сервиса*
## Комплекс мер по снижению рисков угроз

**Угроза**:
- *Нарушение целостности, перехват или подмена данных при передаче между системами.*

**Комплекс мер:**
- Защита от перехвата и подмены данных
	- Применять флаги безопасности (HttpOnly, Secure)
	- HTTPS (TLS/SSL)
	- Аутентификация и подпись запросов (OAuth 2.0, Api-ключи, JWT)
	- Подпись данных (RSA, HMAC)

**Угроза:**
- *Утечка личных и идентификационных данных поставщиком услуги*

**Комплекс мер:**
- Обезличивание данных
	- данные, которые интегратор передает поставщику не должны раскрывать личную информацию, позволяющую идентифицировать пользователя
	- данные, которые интегратор передает поставщику должны содержать только минимально-необходимую информацию
- Шифрование данных поставщиком услуги

**Угроза:**
- *Утеря данных поставщиком услуги*

**Комплекс мер:**
- Резервное копирование данных поставщиков услуги
- Механизм аварийного восстановления данных поставщика услуги

**Угроза:**
- *Недоступность, или медленная работа сервисов поставщика услуги*

**Комплекс мер:**
- Определить метрики производительности и доступности, которым должен удовлетворять внешний сервис

**Угроза:**
- *Компрометация Api, DDoS атаки на Api интегратора.*

**Комплекс мер:**
- Защита контрактов поставщиком услуги
- Механизмы защиты DDoS атак
- Механизмы обнаружения аномалий через мониторинг и логирование

> [!NOTE]
> - выделите протоколы аутентификации и авторизации

- **OAuth 2.0**
    
    Один из наиболее часто используемых протоколов аутентификации и авторизации. Он позволяет сторонним приложениям безопасно получать ограниченный доступ к ресурсам без передачи учётных данных пользователя.
    
- **OpenID Connect (OIDC)**
    
    Эта надстройка над OAuth 2.0 позволяет осуществлять аутентификацию пользователей. OIDC упрощает управление идентификацией в распределённых системах, передавая безопасные идентификационные токены между сервисами.

### Регистрация и автоматическое управление устройствами доступа:

1. Пользователь сообщает девелоперу, что хочет подключить доп. услуги.
2. Девелопер заключает договор (если не заключен) с внешней платформой, на установку и настройку оборудования.
3. Девелопер регистрирует оборудование за квартирой, собственником, другим доверенным пользователем.
4. Пользователь заходит в личный кабинет мобильного приложения, и оставляет свои личные данные биометрии и(или) номерных знаков в специальных формах, и отправляет их девелоперу.
5. Девелопер производит валидацию данных, прикрепляет к этим данным, данные идентифицирующие владельца, и перенаправляет их внешней платформе.
6. Внешняя платформа интегрирует данные для управления устройствами доступа.
7. За непосредственное управление устройствами отвечает внешняя платформа.

### Ручное управление устройствами доступа:

1. Сторонне лицо может запросить доступ вручную, через механизм видео-связи.
2. Устройство доступа посылает сигнал, который приходит на шину событий предприятия через внешнюю платформу.
3. Сервис уведомлений организует уведомление всем пользователям-владельцем устройства о ручном запросе доступа.
4. Если пользователь принимает запрос, то сервис видео-связи предприятия организует потоковую передачу видео от устройства к мобильному приложению.
5. Запросы для других пользователей-владельцев устройства блокируются.
6. Видео-связь позволяет пользователю визуально идентифицировать неустановленное лицо с целью принятия решения о предоставлении доступа.
7. Если пользователь согласен дать доступ, он посылает команду управления сервису предприятия.
8. Если нет, он закрывает соединение
9. Сервис предприятия посылает событие изменения состояния устройства.
10. Внешняя платформа изменяет состояние устройства.
11. Соединение закрывается одной из сторон, или автоматически, спустя установленное время.
